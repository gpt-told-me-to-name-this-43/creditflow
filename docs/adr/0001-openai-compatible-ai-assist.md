# ADR 0001: OpenAI-совместимый необязательный AI-assist

Статус: принято, 2026-10-26. Связано с issue #8; замеры — [ai-eval](../ai-eval.md).

## Контекст и решение

Проверяющий должен подключить внешний или локальный runtime изменением URL, ключа и
имени модели. Используем Chat Completions через `openai.AsyncOpenAI` с произвольным
http(s) endpoint, без host allowlist и без привязки к одному провайдеру. SDK retries
отключены: один повтор на 429/5xx/timeout управляется приложением с Retry-After,
семафором и circuit breaker (5 сбоев, 60 с). Проверка health не вызывает модель.
Пустая конфигурация openai приводит к fallback, а не к отказу финансового конвейера.

Детерминированное ядро владеет расчётом, reason codes, продуктом, ставкой, FSM и решениями.
AI распознаёт предложение полей или объясняет уже сохранённый расчёт. Правила имеют
приоритет при слиянии; interpret не пишет заявку. В заключении разрешены только коды
расчёта, числа — только плейсхолдеры с backend-рендером. Схема, коды, цифры, стоп-фразы,
разметка и длины проверяются после каждого ответа, в том числе replay и fallback.

Предпочитаем `json_schema` (strict); `json_object` и `prompt` передают схему в системной
инструкции для runtime без constrained decoding. Все режимы проверяются одними
Pydantic/прикладными валидаторами. Версии промптов хранятся в отдельных каталогах.

Модель стенда — Llama 3.3 70B Instruct через OpenRouter, по лучшей точности из трёх
open-weights кандидатов до 120B. Qwen3-32B быстрее, gpt-oss-120b ещё быстрее по p95,
но на сохранённом наборе уступают по точности. Llama имеет собственную Community License,
а не Apache-2.0: ссылки и атрибуция — в THIRD_PARTY_NOTICES.md.

## Жизненный цикл и отказоустойчивость

Используем транзакцию Submit, BackgroundTasks и общий recovery-цикл из #7.
PENDING и generation_id создаются при Submit до COMMIT; генерация начинается после него
со своей сессией, без соединения БД на время HTTP. Сохранение — условный UPDATE по id,
generation_id и PENDING; регенерация/recovery не позволяют старому ответу перезаписать
новый. Общий timeout включает очередь, retry и repair. Остановка задачи оставляет PENDING,
который recovery закрывает шаблоном через deadline+15 с (опрос раз в 15 с).
POST сериализуется блокировкой строки. GET читает сохранённое состояние.

Feedback — одна оценка менеджера на отчёт. Регенерация заменяет текст той же строки,
поэтому удаляет его старые оценки в той же транзакции; feedback блокирует ту же строку.
Иначе старый UP мог бы попасть в агрегат новой модели. История оценок отдельных генераций
не хранится: это осознанный предел текущей схемы #6.

`replay` по умолчанию обеспечивает CI/демо без провайдера; hash включает задачу, версию и
канонический контекст. Неизвестный контекст → fallback. `disabled` всегда использует правила
и шаблоны. Запись replay явная, добавляет только отсутствующие контексты.

## Безопасность и trade-offs

Текст клиента только в user/untrusted-блоке; закрывающие теги и управляющие символы
нейтрализуются. Внешняя модель не получает объекты БД, выписки или значения метрик.
Известные ФИО/компании и цифровые идентификаторы маскируются. Нельзя гарантировать
распознавание произвольных третьих лиц правилами: реальные конфиденциальные данные
не предназначены для демо. Внешний провайдер всё же получает минимизированный текст;
для закрытого периметра предусмотрен локальный runtime.

Логи содержат метаданные, без промптов, ответов, API-ключа и тел ошибок провайдера.
Repair не повторяет произвольные коды/ключи из ответа модели. X-Request-ID передаётся
провайдеру. HTTP на внешнем хосте даёт предупреждение, оператор отвечает за TLS.

Дополнительные ограничения: LLM может ошибаться в семантике текста, несмотря на валидную
схему; результат — помощь человеку. Concurrency limit относится к одному процессу API,
breaker находится в памяти и сбрасывается при перезапуске. Нет гарантии доставки фоновой
генерации при остановке процесса, но recovery обеспечивает сохранённый fallback.
Локальный runtime пока не проверен на реальных весах; mocked HTTP его не заменяет.
