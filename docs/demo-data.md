## 1. Ставка и правила округления

**Каталог products-v2, Design 2.5:** investment — **24%** (ключевая 14% +10 п.п.),
working_capital — **25%** (+11 п.п.). Это принятые синтетические тарифы на APP_AS_OF_DATE;
они не являются текущим предложением банка. Старый каталог products-v1 имел обе ставки 24%.
При финализации обнаружено доказанное расхождение: seed и C3/C5/C6 ещё использовали v1.
Их зависимые значения исправлены по независимой Decimal-формуле с prec=50, затем сверены с ядром.
Сценарные исходы, компании, выписки, пороги, формулы и инвестиционные эталоны не менялись.
Обновление уже заполненного каталога 24→25 выполняет миграция 0002, без перезаписи истории расчётов.

Для investment месячная ставка `r = 24 / 1200 = 0,02`; для working_capital — `25/1200`. Коэффициент аннуитета
`A(r, n) = r / (1 − (1 + r)^−n)`, при `r = 0` — `1/n`:

| n, мес. | A(0,02; n) |
|---:|---|
| 12 | 0,0945595966229514852… |
| 18 | 0,0667021021507909289… |
| 36 | 0,0392328525977981494… |
| 48 | 0,0326018355472660932… |
| 60 | 0,0287679658258063318… |

Независимые коэффициенты для 25%: `A(25/1200,12) = 0,09504420326390924568…`,
`A(25/1200,18) = 0,06719181542848436518…`. Golden-тесты используют зафиксированные
литералы, а не вычисляют ожидаемое через функции ядра.

Правила (design §3.4 «Денежные правила»):

- `Decimal`, `prec = 34`, `float` запрещён;
- **пороги — по неокруглённым значениям**: DSCR 1,2479… не проходит 1,25, хотя на экране
  было бы «1.24»;
- платёж `P` хранится и показывается с `ROUND_HALF_UP` до копеек, но DSCR и лимит
  считаются от неокруглённого `P`;
- DSCR показывается с 2 знаками через `ROUND_DOWN`: 0,99218… → `0.99`, не `1.00`;
- лимит — вниз до кратного 10 000 ₽;
- в API деньги и DSCR — строки (`"117698.56"`, `"1.10"`).

Кроме выручки и расходов, в выписке есть операции, которые категоризация обязана
исключить:

- собственные переводы (ИНН контрагента = ИНН компании) — `OWN_TRANSFER`;
- выдача кредита — `LOAN_PROCEEDS`, не выручка;
- возвраты от контрагентов — `UNCLASSIFIED IN`, не выручка.

Поэтому выручка C2 = 1 000 000, а не сумма всех входящих.

## 4. Формулы (design §3.4)

```text
h = месяцев с первой операции до конца окна (≤ 12);  k = ⌊h/2⌋
cfads   = median(revenue[m] − opex[m]) за последние min(6, h) мес.
Δrev    = (Σ revenue[последние k] / Σ revenue[предыдущие k] − 1) · 100
debt    = max(mean(debt_svc) за последние 3 мес., БКИ.monthly_payments_total_rub)
age     = полные месяцы от регистрации до as_of_date
h < 6 или Σ revenue[предыдущие k] = 0  →  SKIPPED + ACCOUNT_HISTORY_INSUFFICIENT

P       = S · A(r, n)                 DSCR  = cfads / (debt + P)
P_max   = max(0, cfads / 1.25 − debt)
limit(t)= ⌊min(P_max / A(r, t), max_amount) / 10 000⌋ · 10 000;
          null, если < min_amount или t вне сроков продукта

score   = DSCR (≥1.50→40, ≥1.25→30, ≥1.00→10, иначе 0)
        + БКИ (CLEAN 30, UNKNOWN 15, MINOR 10, SERIOUS 0)
        + Δrev (≥0%→15, [−15%;0%)→8, <−15%→0)
        + age (≥24→15, 12–23→8, <12→0)
risk    = 80+ LOW, 60–79 MODERATE, 40–59 HIGH, <40 VERY_HIGH; DSCR < 1 → не ниже HIGH
```

Политика: R1 стоп-фактор → `BLOCKED_BY_RULE`; R2 БКИ SERIOUS → `MANUAL_REVIEW`;
R3 DSCR < 1.25 и лимит ≠ null → `COUNTER_OFFER_CANDIDATE`; R4 DSCR ≥ 1.25 и score ≥ 80 →
`ELIGIBLE_FOR_MANAGER_REVIEW`; R5 иначе → `MANUAL_REVIEW`.

Продукты: `investment` — 100 000 … 5 000 000 ₽, 12–60 мес.; `working_capital` —
100 000 … 3 000 000 ₽, 3–24 мес.

## 5. Ручной расчёт по компаниям

### C1 — ООО «ТехСервис»: investment 2 000 000 ₽ / 36 мес.

- `h = 12`, `k = 6`.
- `cfads` = медиана шести значений 400 000 = **400 000,00**.
- `Δrev` = 6 300 000 / 6 000 000 − 1 = **+5,00%**.
- `debt` = max(50 000; 50 000) = **50 000**. `age` = 2021-10-21 → 2026-10-21 = **60 мес.**
- `P` = 2 000 000 · 0,0392328526… = 78 465,7052… → **78 465,71**.
- `DSCR` = 400 000 / 128 465,7052… = 3,11367… → **3.11**.
- score = 40 + 30 + 15 + 15 = **100**, `LOW`.
- `P_max` = 400 000 / 1,25 − 50 000 = 270 000.
  `limit(36)` = min(270 000 / 0,0392328… = 6 881 987; 5 000 000) → **5 000 000**.
- R1–R3 не срабатывают, R4: DSCR ≥ 1,25 и score ≥ 80 → **`ELIGIBLE_FOR_MANAGER_REVIEW`**.
- **Ветка:** одобрение → подписание → выдача.

### C2 — ООО «Пекарня Плюс»: investment 3 000 000 ₽ / 36 мес.

- `h = 12`, `k = 6`.
- `net` за последние 6 мес. по возрастанию: 230 000, 235 000, **238 000, 242 000**,
  245 000, 250 000. Медиана = (238 000 + 242 000) / 2 = **240 000,00**. Порядок в
  исходных данных намеренно не отсортирован.
- `Δrev` = 5 520 000 / 6 000 000 − 1 = **−8,00%**.
- `debt` = max(100 000; 100 000) = **100 000**. `age` = **36 мес.**
- `P` = 3 000 000 · 0,0392328526… = 117 698,5578… → **117 698,56** (M1).
- `DSCR` = 240 000 / 217 698,5578… = 1,10244… → **1.10**.
- score = 10 + 30 + 8 + 15 = **63**, `MODERATE`.
- `P_max` = 240 000 / 1,25 − 100 000 = **92 000**.
- `limit(36)` = 92 000 / 0,0392328526… = 2 344 973,51… → **2 340 000**.
  Аналогично `limit(48)` = **2 820 000**, `limit(60)` = **3 190 000** (M10).
- R3: DSCR < 1,25 и лимит есть → **`COUNTER_OFFER_CANDIDATE`**.
- **Встречное предложение (M8):**
  - по сумме: 2 340 000 / 36 → `P` = **91 804,88**, DSCR = 240 000 / 191 804,88 =
    1,2512… (≥ 1,25), score 30 + 30 + 8 + 15 = **83**, `LOW`;
  - отдельный тест M11 (не основной C2), по сроку: 3 000 000 / 54 → `P` = **91 356,79**, DSCR 1,2542…. На 53 мес. `P` =
    92 321,76, DSCR **1,2479…** < 1,25 — не проходит, хотя округление до 2 знаков дало бы
    1,25. Это и есть правило «пороги по неокруглённым».
- **Ветка:** оффер → принятие → подписание → выдача. До принятия текущий запрос —
  3 000 000; после принятия исходные сумма и срок сохраняются; текущий расчёт ссылается на оффер
  (design §3.7). Принятые 2 340 000 также находятся в `offers[]` и в договоре.

- Остальные данные валидны (без сбоя было бы DSCR 2.54, score 100), чтобы сбой был

## 7. Как проверить

```bash
make demo-data && git diff --exit-code ext-sim/fixtures/   # генератор детерминирован
cd api && uv run pytest tests/scoring/test_golden.py        # код = этот документ
```

Изменение ставки, порогов или исходных агрегатов требует пересчитать разделы 5–6 вручную
и обновить `test_golden.py`. Эталоны нельзя брать из вывода кода.
