# Демо-скрипт CreditFlow (5–7 минут)

Сценарий показа для жюри: один сквозной путь «Пекарни» и короткие ответвления. Эталонные
числа — из [demo-data.md](demo-data.md), их же проверяют E2E (`web/e2e/`, `make e2e`).

## Подготовка (до показа)

1. `make up`, в `.env`: `TEST_RESET_ENABLED=true`, `TEST_RESET_TOKEN=<openssl rand -hex 32>`, `DEMO_AUTH_ENABLED=true`.
2. `make demo-reset` — очередь C3, C6, C7, история решений в сводке, у C1 выданный кредит.
3. Два окна браузера рядом (у каждой вкладки своя сессия): слева клиент
   `director.bakery@creditflow.demo`, справа менеджер `manager.anna@creditflow.demo`.
   Пароль всех учёток — `creditflow-demo`, на экране входа учётки выбираются кнопками.
4. Разрешение 1440 × 900 или больше: карточка менеджера рассчитана на него.
5. По умолчанию `LLM_MODE=replay`: для C1–C7 из демо-состояния заключения записаны заранее.
   По своему тексту заявки записи нет — карточка честно покажет шаблон с причиной
   «Нет записанного ответа модели». Для живой модели — `LLM_MODE=openai` (шаг 6).

## Запасные ответы

- **«Что если два менеджера нажмут одновременно?»** — второй получит «Заявку уже обработал
  другой менеджер», введённый комментарий останется; в БД одно решение (E2E s10, тесты api).
- **«Двойной клик по кнопке?»** — один эффект: `Idempotency-Key` (E2E s11).
- **«Источник данных недоступен?»** — `docker compose stop ext-sim` перед отправкой: баннер
  «Заявка сохранена, но отправить её не удалось», черновик и данные формы на месте (E2E s9).
  После `docker compose start ext-sim` та же заявка отправляется.
- **«Модель выдумает числа?»** — модель пишет числа только плейсхолдерами, значения
  подставляются из расчёта; ответ с цифрами вне плейсхолдеров не проходит проверку и
  заменяется шаблоном с причиной «Ответ модели не прошёл проверку».
- **«Клиент видит score?»** — нет: клиентские схемы не содержат score, DSCR, лимит, коды,
  рекомендацию и AI ни в одном статусе.
- **Сломалось на показе** — `make demo-reset` (≤ 30 с) возвращает демо-состояние.
