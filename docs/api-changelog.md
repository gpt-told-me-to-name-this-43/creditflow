# История изменений API v1

Источник истины контракта — `docs/openapi.json`. Он экспортируется командой `make openapi`
(`scripts/export_openapi.py`) и вручную не редактируется. Коды ошибок описаны в
`docs/api.md`, демо-данные и эталоны — в `docs/demo-data.md`.

## Правила изменения контракта

После тега `contract-v1` фронт генерирует клиент из `docs/openapi.json` и работает на
моках. Поэтому любое изменение контракта:

1. делается отдельным PR с label **`contract-change`**;
2. добавляет запись в этот файл (раздел «Не выпущено»): что изменилось, почему,
   совместимо ли изменение и что делать фронту;
3. содержит перегенерированный `docs/openapi.json`. CI проверяет, что экспорт совпадает
   с закоммиченным (`git diff --exit-code docs/`);
4. для несовместимого изменения требует ревью владельца фронтенда и обновления
   моков в том же PR.

**Несовместимые** изменения (только через `contract-change` и согласование):

- удаление или переименование пути, метода, поля, значения enum или кода ошибки;
- смена типа поля, формата (`Money` — строка `^-?\d+\.\d{2}$`) или nullable → not null
  в ответе;
- новое обязательное поле или ужесточение ограничения во входе (`maxLength`, `gt`,
  `pattern`);
- смена HTTP-статуса или `code` для существующей ситуации;
- новые требования к заголовкам (`Authorization`, `Idempotency-Key`) у существующего
  маршрута;
- появление в клиентских схемах полей, которые клиент видеть не должен (score, DSCR,
  лимит, коды, рекомендация, AI, комментарий менеджера). Это запрещено всегда.

**Совместимые** изменения (запись в changelog обязательна, label `contract-change` не
нужен):

- новый путь или метод;
- новое необязательное поле во входе или новое поле в ответе;
- новое значение enum в ответе — только если фронт обрабатывает неизвестные значения;
- новые примеры и описания.

Реализация стабов в #5/#7/#8 контракт не меняет. Если она требует изменения, оно
проходит по правилам выше.

## contract-v1 — исходная точка

Базовая версия контракта Issue #6 (PR #12). Тег `contract-v1` ставится на проверенный
коммит в `master` после merge PR #12.

- **Маршруты** — 25 путей / 28 операций под `/api/v1`:
  - Auth — `POST /auth/login`, `GET /auth/me`, `GET /auth/demo-accounts`;
  - Онбординг — `GET /consents/texts`, `POST /onboarding/company-binding`, `GET /company`;
  - Клиент — каталог продуктов, заявки, interpret, submit, info-response, offer
    accept/decline, contract, sign challenge и sign;
  - Менеджер — очередь, карточка, decisions, offer-preview, ai-report, ai-feedback, stats;
  - `GET /health`;
  - `POST /_test/reset` — только в local и test при `TEST_RESET_ENABLED`, в OpenAPI
    не экспортируется.
- **Безопасность:**
  - схема `BearerAuth` (JWT), публичны `/auth/login`, `/auth/demo-accounts`,
    `/consents/texts`, `/health`;
  - в #6 проверяется только наличие Bearer, JWT и роли — #5;
  - при `APP_ENV=production` стабы не монтируются.
- **Типы:** деньги и DSCR — строки; входные суммы — целые рубли (`int`, `> 0`);
  изменяющие запросы по заявке содержат `revision`.
- **Ошибки:**
  - единый `ErrorEnvelope {error: {code, message, details?}}`;
  - коды и статусы — `docs/api.md`;
  - инвариант `HTTP-статус == ERROR_STATUS[code]`.
- **Примеры:** у каждого запроса и 2xx-ответа. Строятся из чистых builder-функций
  стабов, время фиксировано (`2026-10-21T09:00:00Z`).

### Согласовать до тега: статусы ошибок

Issue #6 требует, чтобы у каждого эндпоинта в OpenAPI были описаны 401, 403, 404, 409,
422 и 503. Контракт описывает только статусы, которые эндпоинт действительно может
вернуть. Расхождения сделаны намеренно, их нужно согласовать:

| Расхождение | Эндпоинты | Почему статуса нет |
|---|---|---|
| нет 401/403 | `/auth/login` (403), `/auth/demo-accounts`, `/consents/texts` | Публичные маршруты: токен не нужен, роли нет. `/auth/login` отвечает 401 `INVALID_CREDENTIALS` |
| только 503 `HealthResponse` | `/health` | Собственный контракт health (design §3.7), не `ErrorEnvelope` |
| нет 409 | GET-запросы: `/applications`, `/applications/{id}`, `/contract`, `/auth/me`, `/company`, `/credit-products`, `/manager/*` GET, `/manager/stats` | Чтение не меняет состояние: конфликта revision или FSM быть не может |
| нет 409 | `POST /applications` | Новый черновик не зависит от существующих revision |
| нет 409 | `POST …/ai-feedback` | Повторная оценка того же менеджера заменяет предыдущую (design §3.5) |
| нет 503 | все, кроме `submit` и `company-binding` | `PROVIDER_UNAVAILABLE` — только сбой ext-sim (`docs/api.md`), а ext-sim вызывают только эти два. Сбой LLM в `interpret` и `ai-report` даёт `FALLBACK` с правилами, а не 503 |

Если команда всё же требует полный набор статусов, нужны общие коды для этих
ситуаций. Иначе 503 у `GET /consents/texts` описывал бы ложное поведение. Это решение
оформляется записью в этот файл.
